## 1. Confirmed Product Understanding

LifeOS is a unified Personal Operating System connecting long-term aspirations with daily actions in a continuous feedback loop:

$$\text{Set Goals} \longrightarrow \text{Break Down (Milestones/Tasks)} \longrightarrow \text{Execute} \longrightarrow \text{Track Habits/Learning} \longrightarrow \text{Analyze} \longrightarrow \text{Recommend (Daily Focus)} \longrightarrow \text{Improve}$$

### Core Invariants:
1. **Meaningful Outcome Linking:** Every task, habit check-in, and learning session directly informs progress toward high-level goals.
2. **Deterministic & Explainable:** Recommendations, Daily Focus ranking, and Goal Health evaluations use transparent, rule-based algorithms with human-readable rationale—never opaque black-box models.
3. **Calm Productivity & Anti-Slop:** Eliminates guilt-inducing mechanics, notification spam, and artificial AI decoration in favor of clear hierarchy, high readability, and purposeful whitespace.
4. **Zero-Trust Multi-Tenancy:** Multi-tenant privacy and resource ownership are enforced strictly by the backend server; client-supplied IDs are never trusted blindly.

---

## 2. Confirmed Architecture

* **Architectural Pattern:** Modular Monolith in Spring Boot, backed by MySQL as the persistent system of record.
* **Stateless Application Tier:** Spring Boot application instances remain stateless, allowing horizontal scaling behind standard reverse proxies or load balancers.
* **DTO Boundary Layer:** Entity graphs are decoupled from API representations using request/response DTOs, preventing internal schema leaks and over-fetching.
* **Decoupled Frontend:** React (Vite) single-page application communicating exclusively with Spring Boot over HTTPS REST APIs with JSON payloads. Direct database access from React is strictly prohibited.

## 4. Confirmed Database Model

MySQL is the persistent system of record. **For MVP, recommendations are dynamic and stateless; no `recommendations` table is created.**

### Core Relational Schema:
1. **`users`**: `id` (PK, BigInt), `name`, `email` (Unique, Indexed), `password_hash`, `created_at`, `updated_at`.
2. **`goals`**: `id` (PK), `user_id` (FK $\rightarrow$ `users.id`, Indexed), `title`, `description`, `category`, `priority` (`LOW`, `MEDIUM`, `HIGH`, `CRITICAL`), `start_date`, `target_date`, `status` (`ACTIVE`, `PAUSED`, `COMPLETED`, `ARCHIVED`), `progress` (0–100), `created_at`, `updated_at`.
3. **`milestones`**: `id` (PK), `goal_id` (FK $\rightarrow$ `goals.id`, Indexed), `title`, `description`, `target_date`, `status`, `progress` (0–100), `order_index`.
4. **`tasks`**:
   * `id` (PK), `user_id` (FK $\rightarrow$ `users.id`, Indexed, **REQUIRED**)
   * `goal_id` (FK $\rightarrow$ `goals.id`, Indexed, **OPTIONAL**)
   * `milestone_id` (FK $\rightarrow$ `milestones.id`, Indexed, **OPTIONAL**)
   * `title`, `description`, `priority` (`LOW`, `MEDIUM`, `HIGH`, `CRITICAL`), `status` (`TODO`, `IN_PROGRESS`, `COMPLETED`, `OVERDUE`), `due_date` (Indexed), `estimated_minutes`, `completed_at`, `created_at`, `updated_at`.
   * *Structural Constraint:* Standalone, goal-linked, and milestone-linked tasks are all valid. If `milestone_id` is present, the server validates `milestone.user_id == task.user_id` AND `milestone.goal_id == task.goal_id`.
5. **`habits`**: `id` (PK), `user_id` (FK, Indexed), `name`, `description`, `frequency` (`DAILY`, `WEEKLY`), `target_per_week`, `status` (`ACTIVE`, `ARCHIVED`), `created_at`.
6. **`habit_logs`**: `id` (PK), `habit_id` (FK, Indexed), `log_date` (Date, Indexed), `completed` (Boolean), `notes`. Unique constraint on `(habit_id, log_date)`.

8. **`learning_sessions`**: `id` (PK), `learning_item_id` (FK, Indexed), `session_date`, `duration_minutes`, `topic`, `notes`.
9. **`events`**: `id` (PK), `user_id` (FK, Indexed), `title`, `description`, `start_time` (Indexed), `end_time`, `type` (`CUSTOM`, `DEADLINE`, `MILESTONE`, `LEARNING`).
10. **`notes`**: `id` (PK), `user_id` (FK, Indexed), `title`, `content` (Text), `category`, `created_at`, `updated_at`.
11. **`productivity_logs`**: `id` (PK), `user_id` (FK, Indexed), `log_date` (Date), `score`, `task_rate`, `habit_rate`, `goal_rate`, `learning_score`.
12. **`audit_logs`**: `id` (PK), `user_id` (Nullable), `event_type`, `ip_address`, `status`, `timestamp`.

## 5. Confirmed Authentication & Security Model

* **Cookie Management:** Server-managed session credentials using encrypted, `HttpOnly` cookies (`Secure` in production, `SameSite=Strict` or `Lax`).
* **Storage Rules:** Authentication tokens must **never** be stored in browser `localStorage` or `sessionStorage`.
* **CSRF Protection:** Synchronizer token or double-submit cookie pattern protecting all mutating endpoints (`POST`, `PUT`, `PATCH`, `DELETE`).
* **Password Policy:** Hashed using BCrypt (work factor $\ge 12$) or Argon2. Hashes are excluded from all DTOs and log statements.
* **Server-Side Authorization:** Identity is extracted strictly from `SecurityContextHolder`. Client-supplied user IDs in URL parameters or bodies are ignored or rejected. Every query verifies ownership:
  $$\text{WHERE resource.id} = :id \text{ AND resource.user.id} = :authenticatedUserId$$
* **Account Deletion:** Explicit user account deletion (`DELETE /api/v1/users/me`) performs a controlled, programmatic transactional deletion of all user-owned records (goals, milestones, tasks, habits, logs, learning items, sessions, events, notes, productivity logs). Only essential security audit entries are retained.

## 9. Confirmed Recommendation & Intelligence Architecture

* **Stateless Dynamic Evaluation:** Evaluated on demand by `RecommendationService` from live database state; no Redis cache or database table for recommendations in MVP.
* **Goal Status vs. Health Separation:**
  * Lifecycle Status: `ACTIVE`, `PAUSED`, `COMPLETED`, `ARCHIVED`
  * Health State: `ON_TRACK`, `AT_RISK`, `BEHIND`, `COMPLETED`
* **Goal Health Formula:**
  $$\text{Expected Progress} = \frac{\text{Current Date} - \text{Start Date}}{\text{Target Date} - \text{Start Date}} \times 100$$
  * $\text{Progress} \ge 100\% \implies \mathbf{COMPLETED}$
  * $\text{Progress} \ge \text{Expected Progress} - 5\% \implies \mathbf{ON\_TRACK}$
  * $\text{Progress} < \text{Expected Progress} - 5\% \text{ and } \ge \text{Expected Progress} - 25\% \implies \mathbf{AT\_RISK}$
  * $\text{Progress} < \text{Expected Progress} - 25\% \text{ OR } (\text{Target Date} < \text{Today} \text{ and } \text{Progress} < 100\%) \implies \mathbf{BEHIND}$
* **Today's Focus Scoring:**
  $$\text{Task Score} = \text{Priority Score} + \text{Deadline Score} + \text{Goal Health Score} + \text{Overdue Score}$$
  * Priority: $\text{LOW}=10, \text{MEDIUM}=20, \text{HIGH}=30, \text{CRITICAL}=40$
  * Deadline: Due today $= +40$, Due tomorrow $= +30$, Due in 2 days $= +20$, Due in 3–7 days $= +10$, Due $> 7$ days $= +0$
  * Overdue: $+50$
  * Goal Health: Linked goal is $\text{BEHIND} = +30, \text{AT\_RISK} = +15, \text{ON\_TRACK} = +0$, No linked goal $= +0$
  * **Result:** Returns top 5 eligible incomplete tasks (`status IN ('TODO', 'IN_PROGRESS', 'OVERDUE')`) with human-readable explanations.

## 12. Remaining Non-Blocking Technical Risks

These items do not block Phase 1 initialization, but must be observed during implementation:

1. **Local Calendar Dates vs. UTC:** Habit logs track user-local calendar dates (`YYYY-MM-DD` / `LocalDate`). Server evaluation must avoid UTC date shifting around midnight.
2. **JPA Lazy-Loading / N+1 Avoidance:** Loading Dashboard metrics and Goal Details must use dedicated DTO projection queries or `@EntityGraph` to prevent multiple sequential queries.
3. **CSRF Token Handshake:** The Spring Security CSRF cookie must be readable by the frontend or loaded via a token endpoint on app initialization to supply the `X-XSRF-TOKEN` header on mutations.
4. **Mobile Dashboard Vertical Scroll Length:** The single-column mobile dashboard must prioritize Today's Focus and Goal Health at the top, grouping secondary widgets into compact sections to prevent user fatigue.
